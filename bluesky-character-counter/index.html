Character limit and counting rules

The official Bluesky feed post lexicon specifies 300 grapheme clusters in text, and no more than 3,000 UTF-8 bytes. A displayed emoji can contain more than one Unicode code point.

Two limits at once: graphemes and bytes

Bluesky's post record, defined in the AT Protocol lexicon app.bsky.feed.post, restricts the text field to 300 graphemes and 3,000 UTF-8 bytes. A post must satisfy both. For ordinary English the grapheme limit is the one you hit first, because each letter is one grapheme and one byte. For other scripts the byte limit can matter: most Chinese, Japanese and Korean characters use three bytes, and an emoji typically uses four bytes or more, so the byte count grows faster than the visible count.

In practice, 300 graphemes of Japanese is about 900 bytes, well inside 3,000. A post made almost entirely of complex emoji is the realistic way to reach the byte limit first. This counter shows both values and warns on whichever is exceeded.

How to check a Bluesky post

  1. Paste the post text exactly as you will publish it, including mentions and links.
  2. Watch the grapheme count against 300 and the UTF-8 byte count against 3,000.
  3. Remember that links and mentions are stored as text plus “facets” (annotations); the visible link text still counts toward the limit.
  4. Copy the text into the Bluesky app, which is the final validator.

Writing for a 300-character feed

Three hundred characters is a little more than an X standard post, so content usually transfers well between the two, but X weights links at 23 characters while Bluesky counts the link text you include. When cross-posting, check both with the cross-platform checker. For longer ideas, split the text into a reply chain, using the same one-idea-per-post approach described in our guide to structuring a thread.
